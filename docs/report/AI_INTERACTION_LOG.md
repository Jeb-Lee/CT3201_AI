# AI Interaction Log — CT3201 Mini Project

Significant AI interactions during the design and build of *Pyro Pete: Emergency Evacuation*,
by SpectralIntelligence (Lee Tze Hian, Ong Chuan Hau, See Jun Wen).

AI used: **Claude** (Claude Code) for design critique, code, character art, music and the
machine-learning work; **Gemini** for some brainstorm wording and the first character images;
**Kling** for walk-cycle video. Rows 1–9 were reconstructed from the Claude Code session and the
design docs; rows 10–18 from a team interview (29 Sep 2026) and the machine-learning findings
(`pyro_pete_game/ml/ML_Findings/`).

| # | Prompt (summarised) | AI response | Accepted / Partial / Rejected | Student decision | Verification |
|---|---|---|---|---|---|
| 1 | "We plan to use BFS from the rescuer to the nearest occupant; fire is a hazard that drains health. Challenge this." | On a map where hazards are passable‑but‑costly, BFS minimises *tiles*, not *danger* — it will take an extra hazard tile to save a step. | **Accepted** | Treat hazards as **weighted entry costs**; use a cost‑aware search instead of BFS. | Search theory (BFS optimality only holds for unit edge cost); later confirmed by the comparison harness (row 3). |
| 2 | "Suggest alternative search strategies for this and their trade‑offs." | BFS (optimal only unweighted), Dijkstra (optimal, expands widely), A\* (optimal with an admissible heuristic, goal‑directed), Greedy best‑first (fast, heuristic‑only, not cost‑optimal). | **Accepted** | Implement **all four** with a shared per‑tile `cost_fn` so we can compare them on our own map. | Implemented in `pathfinding.py`; behaviour pinned by unit tests. |
| 3 | "Use Greedy Best‑First for the agent — it expands fewer nodes, so it's faster." | Recommended Greedy for speed. | **Rejected** | Use **A\***. Greedy is heuristic‑only and not cost‑optimal on a weighted map. | Built `tools/search_comparison.py`; ran all four spawn→exit over the hazard cost after fire spread. Evidence: **BFS** ≈ 102 cost through 9 burning tiles vs A\*/Dijkstra ≈ 44 through 2; **Greedy** matched A\* on that one fire state, so we repeated it across every stage, three layouts and five fire‑spread times (`tools/greedy_vs_astar_scan.py`): Greedy's route cost more than A\*'s in **98 of 150** situations and was never cheaper. Write‑up in `docs/search_comparison.md`. |
| 4 | "What assumptions are we making in the formulation?" | You're assuming the agent has a full map of occupant locations, which contradicts "the rescuer doesn't know the building" and makes a human‑vs‑AI comparison unfair. | **Accepted** | Add **partial observability**: the agent only knows an occupant once within a vision radius; otherwise it explores toward the nearest unseen area. | Reasoned against the problem statement; observed in‑game that the agent now sometimes commits to a wrong direction and re‑plans — the intended behaviour. |
| 5 | "What could cause our system to fail?" | A locked door on the only corridor makes the goal unreachable; a random tile collapse could wall off spawn / exit / an occupant. | **Accepted** | Add a **key sub‑goal** (fetch the key before a blocked goal) and a **connectivity check** that skips any collapse which would trap a protected cell. | Unit tests: `test_locked_door_key_reachable_with_door_shut`, `test_debris_never_isolates_a_protected_cell`. |
| 6 | "Our maze is a perfect maze. Does that matter for the search comparison?" | Yes — on a single‑path maze BFS, Dijkstra, A\* and Greedy all return the identical route, so the comparison shows nothing. | **Accepted** | **Braid** the maze (remove ~18 % of interior walls) so routing has real choices. | Before/after: with braiding the search comparison shows BFS diverging from A\* (row 3). |
| 7 | "Generate the occupant NPC walk animations as short video clips, then extract frames (same pipeline as the player)." | Produced side‑view ("LR") walk clips only; no walk‑toward/away‑from‑camera; character size and proportions drift frame to frame. | **Rejected** (for the toward/away directions) | Assemble the 4‑direction sets from **mixed sources** — front/back poses from the character sheet, a real side cycle from the clip, mirrored — with a procedural leg‑step for the directions with no footage. | Checked each output against the engine's requirements: 4 directions, fixed sprite height, feet‑anchored, no jitter.
